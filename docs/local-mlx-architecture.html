One local model.
Several distinct jobs.

The model generates text. An inference engine runs it. A harness coordinates its work. Your app decides what it may read, change and remember.

Ollama, llama.cpp and LM Studio can be sufficient for inference. LocalMLX earns its place when we want a reusable Swift API around the MLX engine already inside our app. It is an integration choice, with maintenance costs—not a prerequisite for local AI, privacy, tool calls or Inbox approvals.

      LocalMLX

      The Swift library around an already-loaded model. It handles generation and conversation-cache reuse; it does not own tools or approvals.

      The layers, from model to product

      These are responsibilities, not necessarily separate programs. LocalMLX is a library linked into a Swift process; Pi runs in a Node process in this prototype.

      01 · model data

      Local LLM: weights + tokenizer

      The downloaded model contains learned numerical parameters and the rules for turning text into tokens. Its training, size and quantization strongly affect the answers. The tested model is a local Qwen 27B model in MLX format.

      Model files do not manage an agent, read your journal or approve edits. Changing the harness does not retrain the model. GGUF and MLX models are different packaging/runtime paths, even when derived from the same base model.

      02 · upstream inference libraries

      Apple MLX + Swift model libraries

      MLX supplies the numerical operations. mlx-swift exposes them to Swift; mlx-swift-lm provides language-model machinery, including ModelContainer and ChatSession. CPU/GPU work uses the Mac’s Apple Silicon hardware and unified memory.

      This is where the bulk of inference is implemented. LocalMLX wraps these libraries; we are not writing a new GPU engine. MLX memory model · Swift model library

      03 · our reusable Swift API

      LocalMLX

      MLXSession accepts a loaded model and typed MLXProtocol.Request values. It streams text, returns tool-call data, handles cancellation and reuses the conversation’s KV cache when its history still matches. The cache stores computation from earlier tokens, reducing repeated work.

      The caller loads the model. The library does not download models, execute tools, store journals or schedule multiple apps. A changed history or cancelled generation can require rebuilding the cache. A prayer app can use this layer directly with no Pi or Node.

      04 · process transport

      App bridge or local-mlx-host

      JavaScript cannot directly invoke a Swift object in another process. The bridge carries versioned JSON messages over private stdin/stdout pipes. Holdfast’s PiAgent routes model requests through MLXAgentModel into LocalMLX, or through ServerAgentModel into the reusable HTTP transport. Credentials and local-only data policy stay in Swift.

      Standalone Pi instead launches local-mlx-host, which loads local model files and calls LocalMLX. This helper is an alternative to the embedded app path—not another required process in that path. It is currently a single-client inference helper, not a shared multi-app server.

      05 · Pi provider adapter

      pi-swift-mlx

      This JavaScript package translates Pi’s pi-ai messages, tool schemas and generation options into our Swift protocol. It translates streamed replies, usage and tool calls back into Pi events. The same provider works with regular Pi and Pi Durable.

      The provider has no vault or Inbox. It carries tool declarations and requests, but does not execute them. createProcessTransport serves standalone use; Holdfast injects its own bridge. In Holdfast, the same bridge reaches either LocalMLX or the Swift HTTP adapter. API keys stay in Swift.

      06 · agent harness

      Pi or Pi Durable

      The harness repeats the conversation → model → tool → model cycle and manages context. Regular Pi supplies a coding-agent SDK/CLI and session machinery. Pi Durable is an alternative harness with persisted tasks, checkpointing and recovery; it is not a second agent loop placed after regular Pi.

      Holdfast now uses regular Pi with saved JSONL sessions. Follow-ups retain the conversation, but interrupted jobs are not replayed automatically. Holdfast retains its native receipts, privacy policy and Inbox. Earlier Durable databases remain untouched. Pi Durable

      07 · application behavior and policy

      Tools, retrieval, storage and approval

      Holdfast implements search, note reads and propose_edit. It validates arguments, applies file rules, tracks citations and stores pending changes. The Inbox shows the diff; the user applies it. Snapshotting, stale-file rejection and Undo belong here.

      A prayer app supplies its own journal data, prompts, retrieval and allowed actions. If it needs persistent tools, it can reuse the harness pattern. If it only generates a reflection from supplied text, a direct model request is enough. Neither choice requires sharing Holdfast’s notes.

      08 · product and lifecycle

      Holdfast or the prayer app

      The SwiftUI app owns screens, user preferences, selected model, loading progress and what happens when a user closes a conversation. Holdfast also owns its model-download workflow. The app presents the answer and decides when private context is included.

      LocalMLX currently covers text generation. It is not the complete implementation of a journal, search index, speech system, sync service or model-download manager. Reuse the pieces that actually recur between apps.

      Why not just use llama.cpp,

      We can. The choice is mostly about where inference runs, who manages it and how much integration code we want to maintain.

      LocalMLX is not needed to get MLX

      LM Studio already supports MLX on Apple Silicon. It also documents tool use with MLX models. “We want MLX and tool calling” therefore does not, by itself, justify a custom provider. LM Studio tool-use documentation

      Our reason is narrower: Holdfast already has a loaded Swift MLX model. LocalMLX lets us reuse that implementation and expose it to Pi while keeping inference in the app.

      Native embedding is not unique to MLX

      llama.cpp publishes an XCFramework usable from Swift and provides a SwiftUI example. We could build the same kind of app around it. XCFramework · SwiftUI example

      The benefit of staying with MLX here is continuity with our existing model loader and Swift code. It does not establish that MLX is universally faster, more accurate or easier to maintain.

      One server can serve several apps

      Sharing a library shares code. It does not automatically share a loaded model across app processes. A common service can own the loaded weights and accept requests from both apps; conversations still need separate context and scheduling.

      Ollama provides queueing, residency controls and concurrent-request configuration. LM Studio also documents parallel requests, with runtime-dependent support. Those capabilities are beyond our current helper. Ollama scheduling · LM Studio concurrency

      Local HTTP can still stay on this Mac

      “HTTP” does not mean “cloud.” A loopback service using a local model can keep inference on the machine. Ollama documents a local-only mode; LM Studio supports offline use after the model is downloaded. Ollama local-only configuration · LM Studio offline operation

      Holdfast must still enforce its data rules at the app boundary. Its current HTTP adapter is treated as remote, so allowing it for sensitive local-only notes requires deliberate integration and tests. A process bridge is also not an OS security sandbox.

      What remains ours with every backend

      Domain tools, journal retrieval, citations, proposal validation, approval screens and Undo. A tool-capable model returns a request to act; the configured application or tool runner performs the action. Existing servers also offer agent/MCP features, but those do not automatically implement Holdfast’s rules.

      We have tested correctness with the local 27B model. We have not established a speed or quality advantage for this extracted package over the alternatives. A fair comparison must control model, quantization, context, prompts and tool behavior.

      A file edit, end to end

      Example: “Mark this checklist item as done.” The model proposes an action; the app controls the write.

      1. Build the requestHoldfast supplies the question, relevant context and allowed tool schemas to regular Pi.
      2. Generate a tool requestThe provider and bridge reach LocalMLX. The model asks to read the note; Holdfast validates and performs that read.
      3. Propose the editThe tool result returns through the harness. The next model turn requests an exact replacement using propose_edit.
      4. Save a pending proposalHoldfast checks the file and replacement and writes an Inbox proposal. The original note is still unchanged.
      5. Apply only after reviewThe user chooses Apply Change. Holdfast checks that the original has not changed, saves a snapshot and writes the approved content.
      6. Recover or undoSaved operation IDs/receipts prevent replayed tool calls from duplicating proposals. Undo restores the snapshot; this is separate from harness recovery.

      Replacing LocalMLX with an existing inference server can leave this approval sequence intact. Preserve the native tools and validation, and change only the model connection. Do not substitute ordinary coding-agent file tools if the product promises Inbox review.

      What I would choose for your apps

      These are engineering judgments based on the responsibilities above, rather than claims that one engine wins every workload.

      For Holdfast as a native product

      Keep LocalMLX small and use the existing embedded model. This preserves the loading experience and avoids requiring a separately configured model server. Use regular Pi for the agent loop and saved conversations. Both Pi variants use a Node helper; Durable would additionally bring checkpointed jobs if the app later needs them.

      The native app still needs packaging, model management and lifecycle work. Moving inference in process does not eliminate those jobs.

      For a family of personal apps

      Try an existing local server before building our own shared service. If your priority is “Holdfast and a prayer app use the same loaded model,” Ollama or LM Studio may offer a shorter route. Keep each app’s context and tools separate.

      LocalMLX remains useful when each app should run independently, or when you want direct access to the Swift engine. It is not automatically the easiest way to scale concurrent apps.

      For a first prayer-app feature

      Start with a direct request: the app selects journal entries, constructs a prompt and displays a reflection. LocalMLX or an existing local HTTP service can do that. Add Pi when the feature needs a model-directed sequence of tools; add Durable when interrupted work needs reliable recovery.

      For broader engine flexibility

      Keep app tools above a narrow inference interface. That preserves the option of embedded MLX, embedded llama.cpp or a server. The current pi-swift-mlx package is intentionally an MLX adapter; it should not grow into a replacement for every serving product.

      What exists now

      The names are now LocalMLX for the Swift library, local-mlx-host for the executable, and pi-swift-mlx for the Pi adapter. They now live in three sibling packages: ModelProviders, LocalMLX (including the host), and pi-swift-mlx. The wire format stays at version 1.

      Implemented

      LocalMLX as Holdfast’s default; a standalone Foundation-only ModelProviders package for Ollama, LM Studio and custom servers, with model discovery and Keychain credentials in the app; an inference-only JSONL helper; the reusable Pi provider; regular Pi and Pi Durable integration tests; and Holdfast’s native tools, Inbox approvals, snapshots and Undo. Both engines implement ModelProvider with Inference.Request and Reply; MLXProtocol remains a compatibility alias.

      Not part of this prototype

      A built prayer app, a multi-client model daemon, automatic cross-app model sharing, an iOS integration, or a complete product distribution system, or automatic replay of interrupted agent jobs. The current package targets macOS 15+ and text generation, with one active generation per engine/transport.
